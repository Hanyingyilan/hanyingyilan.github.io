# Five P1 tickets implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement five P1 issues as individually reviewable, sequential local branches.
**Architecture:** Static generation from one content source; native browser enhancement and isolated pure calculation. Commit generated public files to preserve GitHub Pages main:/ publishing.
**Tech Stack:** Node.js standard library, HTML, CSS, native JavaScript; development-only browser tests if required.
**Spec:** [Architecture proposal](../../ARCHITECTURE-PROPOSAL.md), GitHub issue #20.

## Global constraints

Preserve Traditional Chinese public content, existing sources, all #six-* links, and preview noindex. No backend or framework migration. No pushes until permission is available. Stop after five implementation tickets. An implementation review issue is not a PR and does not prove deployment.

## Review focus

The [proposal's implementation contracts](../../ARCHITECTURE-PROPOSAL.md) define failure isolation, publishing inventory and negative-test expectations. The extracted `src/app.js` is a starting point, not evidence that these contracts already pass.

- JS or optional API failure must leave policy text readable (#1).
- No duplicate or omitted IDs when generating all policies (#11/#1).
- Query variants and existing fragment links retain consistent URL behavior (#2).
- Crawler rules must not hide preview noindex, and contributor docs must not enter the public sitemap (#4).
- Fast calculator input changes must settle on the latest value (#12).

## Merge order and status recording

Merge original docs branch, arch/p1-proposal, then tasks 1–5 in order. Each future PR targets its immediate parent until that parent is merged. After squash/rebase merges, rebase remaining branches onto the new base and verify their incremental diff and tests. Do not force-push without authorization.

Maintain a stack table with branch, base, implementation commit, source issue, review issue, verification and remaining owner/deployment checks. Keep original issues open until all required acceptance criteria are met. “Local implementation complete” and “deployed/accepted” are separate statuses.
